## 0. 前提：上一版为什么必须回退

2026-09-16 晚的 route-B 重构（6 个提交：`7385fa7` B1 → `cc8c949` B2 → `8caa709` B3 → `5c62efe` B4 → `79dad32` D1 → `2b66552` B5）已全部剔除，工作树回到 `14d5071`。这些提交仍可通过 SHA 取回，未在任何分支上。

失败形态：新包在真机上主线程**从不归还**，`[Watchdog] MAIN THREAD BLOCKED for 3.5s → 9.5s → … → 85.5s`，探针停在 `PROMPT BUILD DONE`，被系统以 `0x8BADF00D` 杀掉（不是崩溃）。旧包（`14d5071`）同机同会话**不卡**。

### 0.1 一句话根因

重构把**「同源、按 cell、按内容键」的引擎实测**，改成了**「跨源、全局、无宽度」的写入**，于是"某个宽度下量出的文本高度"被当成"任意宽度下的 cell 高度"读走，`engineFloor` 退化为恒 0，流式 cell 每帧回落到全量实测 → 主线程不归还。

### 0.2 我亲自复核的证据（可复现）

基线里 `engineText*` 全生命周期只有 **1 个写点 + 1 个读点**：

| 角色 | 位置 | 内容 |
|---|---|---|
| 写 | `MiniClaw/Views/Chat/Render/MarkdownTextView.swift:1283-1285` | `cell.engineTextHeight = newHeight` / `cell.engineTextContentKey = cell.contentKey` / `cell.engineTextValid = true` |
| 清 | `MiniClaw/Views/Chat/List/MessageListInfrastructure.swift:546-548` | 随 `lastCalcH`/`seedH` 一起清零（cell 复用/重配） |
| 读 | `MiniClaw/Views/Chat/List/MessageListInfrastructure.swift:729` | `guard engineTextValid, engineTextContentKey == contentKey, engineTextHeight > 0` |

三个关键性质在基线里都成立，且都是**必须保住的不变量**：

1. **同源**——写的是 `MarkdownTextView` 自己量出的、带自身 chrome 的 cell 高度，不是裸文本高度；
2. **按 cell**——存在 cell 自身（`SelfSizingCell.engineTextHeight`），不是全局单例；
3. **按内容键**——读时要求 `engineTextContentKey == contentKey`，内容一变立即失效。

`grep -rn "storeEngineTextHeight" MiniClaw/ --include=*.swift` 在基线**零命中**：这个函数是重构引入的。重构版 `MessageListInfrastructure.swift:523-529` 把它写成对 `HeightStore.shared` 的全局写入，参数是 `constrainedWidth: 0` + `returnedWidth: .greatestFiniteMagnitude` + `priority: .measured` —— 无宽度维度却标成最高优先级；同时基线注释 `14d5071:511-517` 已经把这个坑记录为"此前修过的 bug"，重构版把那段注释**原样保留**却把守卫改回了旧的宽松形式。

> 教训直接写进纪律：**一段注释记录"某形态已修"时，改动必须逐字比对它守着的那行代码，不能只留注释。**

### 1.4 我们明确不做什么

11 条"看着能省、实际造环或改命中集合"的禁区 + 5 条流程禁区，见 §7。其中三条最关键：

### 2.4 【首要候选成因】拖动期收缩绕过 deferred 闸门：一个访问器承担了两个问题

> 这是 2026-09-16 读源码得到的、**用户症状「拖动期重叠」与「3 行消失」的首个有完整证据链的候选成因**。
> 分界必须说清：**机制与代码事实已证；它是否真的在真机上高频发生，尚未测量**（探针已埋，见 §3.1 M10）。

**几何前提**：`prepare()` 用单调 `y += h` 生成帧，所以**同一趟布局内不可能重叠**。因此"拖动期重叠"只有一种成因——**某处收缩了高度却没有重跑 `prepare()`**，后面的 item 仍拿着旧的 `y`，压到前一个身上。这正是 `deferSelfSizing`（拖动期只拒收缩）要防的事。

**闸门本体的两处代码事实（已证）**：

| # | 事实 | 证据 |
|---|---|---|
| 1 | 闸门用 `currentEntry(at:)` 判断"能否保护" | `MessageListLayout.swift:402` `let hasCached = currentEntry(at: index) != nil`，随后 `if hasCached { … return false }`（拒绝收缩） |
| 2 | 但 `currentEntry` 回答的是**有效性**，不是**保护性** | `:74-78`：`guard let stored = e.key, let cur = contentKeyByIndex[index] else { return e }` → `return stored == cur ? e : nil`。**键不一致即返回 nil** |

**触发链（已证）**：`setContentKey(_:at:)`（`:734-736`）**只写** `contentKeyByIndex`、**不同步** `heightEntries[index].key`；其调用点之一是 **`MessageCollectionView.swift:444`（`configureCell` 路径）**。于是：

```
拖动 → 新 cell 进视口 / 流式块内容变化
     → configureCell → setContentKey(新键)
     → heightEntries[i] 仍带旧键 ⇒ currentEntry 返回 nil ⇒ hasCached = false
     → 闸门整块被跳过（注意是"跳过"，不是"放行"：连 deferredHeights 都不记录）
     → 返回 mustInvalidate ⇒ 拖动期真实收缩
```

**为什么此前没修好（已证）**：`:395-401` 的注释记录了该闸门**曾因同类事故被加宽过一次**——原先只把 `source == .measured` 当"已缓存"，导致 `.estimated/.precalc` 的 cell 不受保护，真机出现 `liveShrink −160pt`（`phase=decel` 19 条）。那次把它改成"**任何已有条目**都算已缓存"。**但 `currentEntry` 在键过期时返回 nil，所以"任何已有条目"这句话在键过期时并不成立** ⇒ 修正是不完整的：根因不是"哪些 source 算缓存"，而是把**有效性**判据当成了**保护性**判据。

**另一条并行绕过形态（已证）**：`prepare()`（`:186` 起）**完全不写 `heightEntries`**；条目只有 **4 个写入口**（`:80 setEstimatedHeight`、`:84 setPrecalcHeight`、`:353 applyDeferredHeights`、`:467` 提交路径）。因此**从未被播种的 index 连条目都没有**，同样 `hasCached = false` 而绕过闸门。

**结论与处置**：
- **已证**：闸门在 `hasCached == false` 时完全失效，而 `hasCached` 会在"键过期"与"没有条目"两种常见情形下为 false；其中"键过期"正是**拖动期新配置的 cell 与流式块**的常态。
- **未证**：这在真机上发生的频次与幅度，以及它是否足以产生肉眼可见的重叠。
- **处置**：先埋探针 **M10**（已提交 `d351f25`，只观测不改返回值，1s 节流 warn）：`keyStale` / `noEntry` 两个计数 + `idx/orig→pref/delta/两把键`。等真机拖动取样后，再决定是否执行 **S2.5**（把保护性判据与有效性判据分开，例如闸门改用 `heightEntries[index] != nil`）——那是**行为变更**，必须先有度量。

#### 2.4.1 ⚠️ 继续核对后，本假设**被显著削弱**（记录在案，避免自我欺骗）

把 `configureCell` 读完整后，找到了**关闭该窗口的修复路径**（`MessageCollectionView.swift:475-487`）：

#### 2.7.1 症状 1 / 2 可能是**同一个根因的两种表现**（重要推论）

`MarkdownTextView.init` 设了 `clipsToBounds = true`，而 `[TruncL]` 的 `clipped` 判据测量的是 `textView.frame.maxY > cell.contentView.bounds.height` —— 说明 **textView 自身可以伸到 cell 之外，是否被裁取决于 cell 层是否裁剪**。

⇒ 若 cell 层**不裁剪**：帧矮于内容 → **画到下一块上（症状 1「重叠」）**；
⇒ 若 cell 层裁剪：同样的帧矮于内容 → **多出来的行看不见（症状 2「3 行消失」）**。

**也就是说这两个症状可能不是两个 bug，而是"cell 帧矮于内容"在不同裁剪配置下的两种呈现。** 这条推论把搜索空间收窄了一半：**不必分别找"重叠源"和"消失源"，只需找"谁让 cell 帧矮于内容"**——而上面那个 0 高度播种正是候选之一。

#### 2.7.2 ❌ 上一节的推论**已被证伪**：这套配置下 cell 一定裁剪，帧也一定不重叠

> ⚠️ **本节结论亦已被 §2.9 部分推翻，务必连带阅读。**
> 本节证明的是：**`prepare()` 的产物 `itemAttributes` 内部**帧不重叠（M13 = 0/44）、且 cell 一定裁剪。
> 但集合视图实际使用的帧还可能来自 **PLAF 提交路径**（不经过 `prepare()`）—— M15 实测**屏上帧与
> `itemAttributes` 背离最多 2015.6pt** ⇒ **屏上确实会重叠**。本节只能说明"几何路径中**布局数据侧**不是病灶"，
> **不能**说明"屏上不会重叠"。这正是 M13 埋点位置的盲区（详见 §2.9.2）。

继续核对后，§2.7.1 的"两种呈现"推论**不成立**。两条硬事实：

| # | 事实 | 证据 |
|---|---|---|
| 1 | **cell 一定裁剪内容** | `SelfSizingCell` 的**两个初始化器**都设 `contentView.clipsToBounds = true`（`MessageListInfrastructure.swift:459`（`init(frame:)`）与 `:463`（`init?(coder:)`））⇒ 必然生效 |
| 2 | **没有任何子视图加到 cell 本身**（因而没有绕开 contentView 裁剪的图层） | 全仓 `addSubview` 在聊天列表内只有两处：`MessageCollectionView.swift:242`（host view）与 `MessageListInfrastructure.swift:120`（collectionView）；**没有 `cell.addSubview` / 没有往 `contentView` 之外挂东西** |

⇒ **帧矮于内容只会表现为"内容被裁掉"，不会表现为"画到下一块上"。**

再看症状 1 的另一条可能——**帧与帧本身重叠**——同样被排除：

| # | 事实 | 证据 |
|---|---|---|
| 3 | `itemAttributes` **只有一个写入点**，且在 `prepare()` 内 | 全字段引用：`:175` 声明、`:199 removeAll`、`:200 reserveCapacity`、**`:271 append`（唯一写）**、`:302/:313/:323-324/:355/:451-452` 全为读 |
| 4 | `prepare()` 用单调 `y += h` 生成，故同一趟内帧不重叠 | `:186-293`（已核 `prepare()` 内**不写** `heightEntries`） |
| 5 | `layoutAttributesForItem(at:)` 直接返回同一个缓存对象 | `:322-324` `return itemAttributes[indexPath.item]` |

⇒ **帧之间不可能重叠。**

**结论（重要）**：
- **§2.4 与 §2.7 都解释不了症状 1「重叠」**——它们能解释的只是"内容被裁"（即症状 2）。这一点必须写清，否则会拿着两个只解释症状 2 的候选去追症状 1。
- **症状 1 的"几何类"解释已全部排除**。剩下的只有三类，且都不在几何层：
  - **(A) 同一区域出现两段不同内容**（绘制/布局在同一 cell 内互相压住）。工程里**确有此类先例且已修**：`MarkdownTextView.swift:1451-1453` 的注释记录了"TextKit 给附件附近字符算出的 bounding rect 会覆盖附件的可视区，导致引用条压住表格/图片"，修法是**把附件矩形从条带绘制里排除**。⇒ 这类问题在这个工程里是真实存在过的形态。
  - **(B) 同一块内容出现两遍**（重影/重复）：cell 复用或条目身份重复导致。
  - **(C) 我尚未设想的第三类**（因为我的假设都建立在"几何"前提上，而该前提已倒）。

**下一步不再是猜，而是取观察**：症状 1 的**视觉形态**决定了它属于 (A)／(B)／(C)，而这三类的排查方向完全不同。已请用户提供一张截图或一句形态描述（见 §2.7.3）。

### 2.8 【症状 2 的**非几何**候选】`TextFadeAnimator` 把字符 alpha 压低后未还原 ⇒ 文字不可见

> 分界：**机制与"诊断不可见"两点已证**；它在真机拖动/流式中是否发生，待 `[FadeLeak]` 取样（探针已就绪，见提交 `a1ad120`）。

**为什么转向非几何**：§2.7.2 已证 cell 一定裁剪、帧一定不重叠 ⇒ §2.4/§2.7 只能解释"内容被裁"，解释不了症状 1。而"文字消失"完全可以**不经几何**发生——只要字符的 `foregroundColor` alpha 被压低后没还原。

**机制（已证）**：`TextFadeAnimator` 的流式渐显实现是**直接把 `.foregroundColor` 设成低 alpha**（`Render/TextFadeAnimator.swift:266-273`：`storage.addAttribute(.foregroundColor, value: w.originalColor.withAlphaComponent(eased), range: w.range)`）。故"压暗未还原"＝**字符停在低 alpha ＝ 文字不可见**。

**这不是理论担忧，工程自己就有证据**：`TextFadeAnimator.swift:188` 的日志是

**改**：`MessageListLayout.swift:402` 的闸门判据。当前是

```swift

```

而闸门需要回答的是**保护性**：*这个 index 有没有帧可以保护*。故改为用"条目是否存在"作保护性判据，**同时保留** `currentEntry` 作为有效性判据供它原来的用途（`mustInvalidate` 的 `.measured`/阈值分支、以及 `:730` 的 `hasMeasuredHeight`）。

```swift

```

- `[DeferShrink] Σ|delta|` 是否从"几十 pt"涨到"数百 pt"（若涨太多，说明被拒的收缩变多 ⇒ 空白变多，需按注释里说的"只对视口内放行"）；

**验收**：M10 的 `keyStale`/`noEntry` 归零（或只剩 noEntry 且已单独处理）；三症状不变坏；`[DeferShrink]` 幅度被记录在案；`[Watchdog]` 为 0。

#### S2.12 — commit 之后同步帧模型（**症状 1 的第①刀，现为首要；改法待 M16 判别**）

**准入：已满足，且是本会话唯一"索引一致 + 数值吻合"的硬证据。**

> `[CellSizing] INVALIDATE idx=57 delta=2016 est=2550 → pref=4566 cached=false`
> 与 `[Stage0][M15] 最坏=2015.6pt @idx=58`

**已读清的代码事实**（决定了这条链的形状）：

| 位置 | 做什么 | 不做什麼 |
|---|---|---|
| `MessageListInfrastructure.swift:676 commitHeight(_:into:)` | 改**属性对象**的高度；顺带记 `committedTextHeight` | **不碰** `itemAttributes` 里其它条目的 frame |
| `MessageListLayout.swift:567 invalidationContext(...)` | `super.invalidationContext`（让集合视图采用 preferred）+ `setEntry(newH, .measured)` + `pendingAboveShift` | **不碰** `itemAttributes` |
| `MessageListLayout.swift prepare()` | **`itemAttributes` 的全字段唯一写入点**（`append`） | — |

⇒ **若一次提交让 idx=57 增高 2016pt 而 idx=58 的屏上 frame 未随之平移，两者之差恰为 2016** —— 这正是 M15 读到的 `2015.6pt @idx=58`，也正好解释用户所述"文字在上方"：**57 变高压住 58，而 58 因 index 更大而绘制在其上**（全仓未设 `zIndex`）。

**改法取决于一个尚未判别的事实（M16 已埋，`aaf856e`，用现成的 `prepareCallCount` 当判别键）**：

| 分支 | M16 会显示 | 含义 | 改法 | 风险 |
|---|---|---|---|---|
| **A** | `preparesNow == preparesThen`（**未**重跑） | 提交后 `prepare()` 没跑 ⇒ `itemAttributes` 仍是旧的 | **提交后同步/强制重跑**：在 `invalidationContext` 返回前（或 `shouldInvalidateLayout` 返回 true 之后）确保布局被重算；或提交时**同步平移后续条目的 frame** | 中（增加布局次数，须量 `[cv-layout]`） |
| **B** | `preparesNow > preparesThen`（**已**重跑）却仍背离 | `prepare()` 读了 `heightEntries` 却得出不同结果 | 转向检查 **`setEntry` 是否被优先级闸门静默拒绝**：`:141` `if let existing = currentEntry(at:), rank(existing.source) > rank(source) { return false }` —— 调用方**不看返回值**，被拒时 `heightEntries` 保持旧值而集合视图已采用新高度 ⇒ 背离 | 中-低（`setEntry` 返回值当前被忽略，可能是**静默失配**的根源） |

**⇒ 所以本轮只埋探针、不改行为**：两条分支的改法完全不同，赌错方向会同时改错地方并掩盖真因。

#### S2.12-A 的实现规格（分支 A 若成立的实现，已写到代码级）

**判据复核（离线推演）**：`setEntry` 对 `.measured`（rank 3，最高）**不可能被优先级闸门拒绝**（`rank(existing) > 3` 永假），且 4566 有限非负 ⇒ `setEntry(4566, .measured)` **必被接受** ⇒ `heightEntries[57]` 已是 4566。
**⇒ 若 `prepare()` 在提交后重跑，`itemAttributes[57]` 必然取到 4566，背离不会发生。**
**⇒ M15 读到 2015.6pt 背离 ⟹ `prepare()` 在提交后【未】重跑（或重跑发生在下一帧之后）。** 即**分支 A 几乎必然成立**（M16 只是把这条演绎变成实测确认）。

**实现（分支 A 专属）**：**提交时同步平移后续条目的 frame**，而非强制 `prepare()`。

```swift
// MessageListLayout.invalidationContext(...) 内，setEntry 之后：
if setEntryAccepted, abs(delta) > 0.5 {
    // 同步平移 itemAttributes 中 index 之后所有条目的 minY，
    // 使布局的帧模型立刻与"已采用的高度"一致 —— 消除分叉窗口。
    if index + 1 < itemAttributes.count {
        for j in (index + 1)..<itemAttributes.count {
            itemAttributes[j].frame.origin.y += delta
        }
    }
}
```

**为什么比"强制 prepare()"优**：

| | 平移后续 frame（本方案） | 强制 `prepare()` |
|---|---|---|
| 成本 | O(后续条目数)，纯内存指针算术 | O(全表重算)（`prepare()` 全量重排） |
| `[cv-layout]` 影响 | 无（不加布局 pass） | 481.2ms 已偏高，会恶化 |
| 一致性 | `itemAttributes` 与屏上帧**立即**一致 | 下一帧才一致 |

**必须同时处理的三个边界**（实施时逐条核对）：

1. **`totalHeight` 同步**：`prepare()` 里 `totalHeight = y`（`:282`），平移后须 `totalHeight += delta`，否则 `collectionViewContentSize` 与帧尾部不符 ⇒ `contentSize` 误导滚动。
2. **`deferSelfSizing` 期间**：`[DeferShrink]` 已把收缩延后进 `deferredHeights`，本平移只处理**被采纳的** delta（即 `shouldInvalidateLayout` 返回 true 的那次），与延后项**互不重叠**（`shouldInvalidateLayout` 返回 false 时根本不会走到这里）。
3. **`pendingAboveShift` 与本平移的互斥**：`pos == "inside"` 时 `pendingAboveShift += delta`（`:527`）用于**解冻时锚定**；本平移是**立即**把帧挪到位。两者**不冲突但会叠加视觉位移** —— 需确认 `pos == "inside"` 时是否应跳过平移（延后语义）。**这是本实现唯一不确定的点，实施前必须先读 `applyDeferredHeights` 与 `takePendingAboveShift` 的消费端**。

**验收**：`M15屏上背离` 降为 0；`[cv-layout]` 耗时不恶化；`totalHeight` 与帧尾部一致（`[prepare] totalH=` 与末帧 `maxY+spacing` 相等）；三症状按用户指示**不作为本步验收目标**。
**回滚**：单独提交，失败即 `revert`。

**风险（诚实的部分）**：第 3 条边界（`pos == "inside"` 时平移 vs 延后的语义冲突）**是我目前唯一没有把握的点**。若处理不当，会把 §2.9.4 已记录的 `[SettleAnchor] pendingΣ=+20.0 → 顶部被推 20pt` 那类抖动重新引入。所以实施顺序是：**先只对 `pos == "below"` 做平移**（视口下方，不影响可见内容，最安全），`"inside"` 留给原有延后机制，等 `[SettleAnchor]`/`[DeferShrink]` 数据确认无冲突后再放开。

**风险（两种改法共同）**：都不得恶化 `[cv-layout] slow layoutSubviews`（当前 481.2ms 已偏高）。
**与 `deferSelfSizing` 的关系**：`[AttachHang] ALLOW through defer` 那条放行路径是分叉的制造者之一，故本步与 S2.3（尾部三连条件化）必须**分开提交**，以免归因不清。

**验收**：`M15屏上背离` 降为 0（或以 `M16` 的结论解释为何仍非 0）；`[cv-layout]` 耗时不恶化；三症状不变坏（按用户指示，症状 1 的修复排在本次改造之后，故本步**不以消除重叠为验收目标**，而以"背离归零"为技术判据）。
**回滚**：单独提交，失败即 `revert`。

**验收**：`M15屏上背离 = 0/自洽 N 次`；`[cv-layout]` 耗时不恶化；三症状不变坏。
**回滚**：单独提交，失败即 `revert`。

## 10.8 Stage 4 度量与「块级 memo」（2026-09-17 21:00–21:30）

### 10.8.1 `[RND]` 为什么一直看不见 —— 它在**静音名单**里

`AppLogger.quietInfoCategories = ["RenderCache", "MarkdownRenderer"]`（`AppLogger.swift:168-170`）
⇒ `MarkdownNSRenderer.render` 里那条 `[RND]`（info 级）**既不落盘也不打印**：实测当天日志 `[RND]` **0 条**。
Stage 4 的病因其实**一直被记录着，只是看不见**。处置：慢样本（≥20ms）改走 `warn`（量很小，会话约 10–20 条）。

### 10.8.2 病因（真机实测）

- **逐块渲染占 84%**，合并拼接占 16%（11 条样本 349.6ms / 64.3ms）。
- **同一条消息被反复整体重渲**：`mid=1FCF8189` 一次会话 **7 次**、`mid=568252F9` **3 次**。
- **`ctor` 恒为 0**（158 次累计 **0.1ms**）⇒ **S4.5「复用 renderer」正式证伪**：
  `MarkdownNSRenderer(baseFontSize:)` 是惰性初始化，构造根本不花钱（它要消除的开销不存在）。

### 10.8.3 ⚠️ `[M7]` 的覆盖面缺口（必须记住）

`[M7]` 只包 `renderMarkdownBlocks`（**throwaway renderer**），而**真正跑流式的是
`MarkdownView.rendererCache` 那一路（复用渲染器）** ⇒ `[M7]` 的会话累计**不能代表流式路径**。
因此"上一会话 13111ms"与"本会话 208ms"**不可比**；§10.7.5 里写下的
「会话级 13.1s → 3s 量级」目标**不成立，撤回**。补：新增 `[RNDΣ]`（每渲染器累计 n/合计/逐块/合并/worst）。

### 10.8.4 块级 memo（已落地，`MarkdownSupport.swift`）

三条**构造性**边界：① 产物含 `.attachment` ⇒ 不入表（天然排除表格/代码块/公式/图片，且不扰动
`codeBlockIndex`/`tableIndex`）；② 命中要求 `blockId` 一致，不一致则**覆盖**（不会返回错内容、表不膨胀）；
③ 字号/主题变化 ⇒ 整表失效。

**实测（PID 10820）**：

| 渲染器 | n | 合计 | 逐块 | memo 归因 |
|---|---|---|---|---|
| `rnd=640f63 mid=5EC748D7` | 15 | 4.8ms | 1.8ms | hit=20 miss新=22 miss换id=3 含附件=15 |
| `rnd=640f63 mid=7EC8FC1E` | 21 | 16.0ms | 12.9ms | hit=33 miss新=31 miss换id=4 含附件=20 |
| `rnd=ffc7b8 mid=8EA3B4FC` | 1 | **90.6ms** | 89.4ms | hit=0 miss新=14 含附件=0 |

- ✅ **命中成立**，且 `miss换id` 很小（3–4）⇒ `blockId` 稳定、前提成立；含附件块被正确排除。
- ⚠️ **收益是有条件的**：只有"**大消息被反复渲染**"时才省。本会话那个 90ms 的大消息只渲染 **1 次**
  （`n=1`）⇒ 没有可复用的东西，本会话**体现不出收益**；而上一会话那条 33 块消息确实被渲染了 3 次。
- ⚠️ **剩下的成本是冷渲染本身**：14 块 / 2074 字符 = **89.4ms**，≈ **6.4ms/块**。
  按每块字符数归一后与上一会话 ~2ms/块同量级 ⇒ **未见 memo 开销**（不是它拖慢的）。
