## 二、缺口 ① 的决定性实验

| 时刻 | `[MCP-发现]` | `[Cache指纹] tools=` |
|---|---|---|
| 21:33:18 | `listTools 开始 (forceRefresh=true)` ← 建表 | — |
| 21:33:49 / 21:33:52 | 缓存命中, 5 个工具 | `6f2dab3f` |
| 21:34:57 / 21:35:00 | 缓存命中, 5 个工具 | `6f2dab3f` |
| **21:39:03** | **缓存过期(344s), 返回旧列表并后台刷新** | `6f2dab3f` |
| **21:39:06** | **后台刷新失败：DiscoveryTimeout** ← 失败名单被写入 | — |
| **21:39:08** | **缓存过期(349s), 返回旧列表并后台刷新** ← 仍在 60s 失败窗口内 | **`6f2dab3f`（未变）** |
| 21:39:12 | — | `6f2dab3f`（未变） |

**判据**：21:39:06 已写入失败名单。**旧实现**在 21:39:08 会走"失败名单优先"分支直接
`throw DiscoveryTimeout()`（**连一行 `[MCP-发现]` 都不会打**）⇒ 调用方丢弃该服务器**全部工具**
⇒ `tools=` 必变。实测它打印了「返回旧列表」且哈希**未变** ⇒ **修复成立**。

**附加证据**：21:39:12 服务器收到 **4 次 `tools/call`**（id=5/7/8/9）⇒ 工具不仅仍在列表中，而且**真的可调用**。

## 三、交叉验证：固定表确实免网络

建表（21:33:18）之后，设备侧连续 4 次「缓存命中」，而服务器侧 `requests=7 / tools_list=4`
**零增长** ⇒ 纯吃内存表，一次网络请求都没发。

## 八、缺口 ②（后台刷新静默换表）—— 实测**关闭为非问题**

**风险假设**：后台刷新在任意时刻落地 ⇒ 若它落在**一条消息之内**（agent loop 会连续调多次模型），
模型就会在同一轮里看到两套工具。

**实测**（服务器 `n` 5→8 制造真实变化；表在 21:46:38 过期）：

| 时刻 | `[MCP-发现]` | `[Cache指纹]` |
|---|---|---|
| 21:47:03 | **缓存过期(324s)，返回旧列表并后台刷新** + **后台刷新完成, 8 个工具** | `#1 tools=6f2dab3f`（旧表 5 个，14786tok） |
| 21:47:07 | 缓存命中, 8 个工具 | `#1 tools=22b836aa`（新表 8 个，15248tok） |
| 21:47:10 | — | `#2 tools=22b836aa`（**同一条之内不变**） |

**结论**：`tools=` 只在**两条消息之间**变一次，**从未在一条消息之内变过** ⇒ 后台刷新的生效点
天然落在轮与轮之间，等价于"延后一轮生效"（与代码注释一致）⇒ **不需要"暂存 + 轮首切换"**，不写代码。

**顺带量化**：5 个工具 `14786tok` → 8 个工具 `15248tok` ⇒ **3 个工具 = +462 tok ≈ 154 tok/个**
（与 §四 的 770/5 完全吻合）。

## 九、缺口 ④（工具名嵌 `server.id`）—— 实测证实 + 修复

**实验**：把 `mcptest` 服务器**删掉再用完全相同的参数加回来**（名称/URL/传输一字未改）。

| | 改名**前** | 改名**后** |
|---|---|---|
| 服务器 UUID | `7E919C0F-…` | `E6F91717-…` |
| 工具名（按 App 算法算出） | `mcp__mcptest_7e919c0f__test_tool_0_30fb8bcd` | `mcp__mcptest_e6f91717__test_tool_0_54f20326` |
| 工具数 | 8 | **8（相同）** |
| token 数 | 15248 | **15248（完全相同）** |
| **`[Cache指纹] tools=`** | `22b836aa` | **`e4be6796`（变了）** |

**结论**：内容与 token 数完全不变，仅因配置实例 UUID 改变就换哈希 ⇒ 工具段整块变化 ⇒
**上下文缓存从 tools 段起整段失效**（无谓失效，实测证实）。

**根因**：工具名由**实例身份**（`server.id`）决定，而不是由**定义**决定。

**修复**：`providerSafeName` 改用 `serverDefinitionKey(server)` —— 由用户可见且重建配置时不变的
四项派生（`name` / `endpointURL` / `command` / `args`，带分隔符避免拼接歧义）；名字形状不变。
不用 `lastStatus`/`lastError`/`lastCheckedAt`（易变，会让名字随运行状态抖动）。

## 十、缺口 ④ 修复的复验（决定性）

修复后按同样方式再验一次：**删掉 `mcptest` 再用相同参数加回来**。

| | 修复前 | 修复后 |
|---|---|---|
| 重加**前**的 UUID | `7E919C0F` | `E6F91717` |
| 重加**后**的 UUID | `E6F91717` | **`4E874418`（确实又变了）** |
| `[Cache指纹] tools=` | `22b836aa` → **`e4be6796`（变了）** | `b3a4c294` → **`b3a4c294`（未变）** |

时间线：`21:52:26 listTools 开始 (forceRefresh=true)`（重加后的强刷）→ `21:52:34 tools=b3a4c294`，
与重加前的 `21:51:59 tools=b3a4c294` **完全一致** ⇒ **无谓失效被消除**。

（`b3a4c294` 与前两个值不同是预期的：命名规则本身变了，所以修复上线后的**第一次**会变一次，
那之后稳定。工具数 8、token 数 15248 全程一致。）
