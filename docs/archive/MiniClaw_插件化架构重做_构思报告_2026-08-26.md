# MiniClaw 插件化架构重做 — 总体方案与开发计划（v5 终稿）

> 状态：方案已定稿，未动任何代码。本文件为各轮讨论的最终收敛结果，后续直接进入实施。
> 目标：把 MiniClaw 改造为「核心底座 + 插件系统」双大板结构；插件统一为 `.mpk` 压缩包；项目与插件规范均开源；现有功能行为不变。
> 事实依据：所有模块名、字段、资源目录均来自当前仓库实读（`MiniClaw/Services/`、`MiniClaw/Resources/`、`MiniClawCLI/`）。

## 〇、决策总览（所有已决项，便于一眼看全）

**架构方向**
- 双大板：**核心底座**（只暴露扩展点契约，不含策略）+ **插件系统**（`.mpk`，含内置默认插件）。
- 统一插件包 = `.mpk`（zip 容器内嵌固定目录 + 一份 `plugin.json` 清单）。
- 统一开发格式：所有插件共用同一目录骨架 + 同一份 `plugin.json`，开发者只声明 `type`（用于调整哪个功能）+ `category`，按 `type` 填对应内容文件。
- 开源：主仓库开源 + 独立插件规范仓库 `miniclaw-plugin-spec`，用户凭规范即可开发/打包/发布。

**本轮（v4）拍板的 6 项**
1. **`plugin.json` 强制**：不存在旧兼容；无 `plugin.json` 的包一律拒绝加载。内置技能直接升级为带 `plugin.json` 的 `.mpk`，不再保留无清单的旧 `SKILL.md` 扫描路径。
2. **模型插件请求头策略（见 §四·3）**：默认**插件不声明 `extra` 请求头**，附加头走现有 `LLMProvider.customHeaders` 手动配置（与今日一致），因此**不引入插件 extra 头护栏**（无不可信插件注入任意头的攻击面）。模型插件协议只声明 compat 族 / auth 方法与认证头格式 / baseURL 提示 / 模型能力；`auth` 段仅含认证格式，不含 `extra`。若未来开放插件 extra 头，再启用 §四·3 的安全护栏方案。
3. **主题插件 v1：按建议做**——落地 `ui.theme` 扩展点 + 1 个示例主题插件验证链路，不铺开。
4. **原生扩展（第三方 `core.extension`）：明确不做**，且规范明确禁止插件携带 Apple 不允许的代码（JIT、可执行原生二进制、私有 API、需特殊 entitlements 的能力等）。插件能提供的工具实现仅限 `script`(iSH 沙箱) 与 `mcp`(外部服务)；`native` 仅用于"内置工具经核心登记"（不引入第三方原生代码）。
5. **开发顺序：重排为阶段化计划**（见 §八）。每个阶段 = 插件化**一个**功能 + 打基线 commit + 模拟器编译 + **真机 device build + 功能自测**，通过才进下一项，不通过回退该阶段。
6. **首个真机验证项：从阶段 1 `skill` 起步**（纯内容搬家、风险最低、最快跑通真机闸门机制）。

**历轮已决（回顾）**
- 7 个厂商「留代码、隔离、不引用」：移入 `Services/Providers/Deprecated/`，不进活动 `ProviderType`/`LLMProviderFactory`。
- 图标统一 SF Symbols：用户 `icon` 声明优先，否则按 `category` 取默认。
- 工具插件走 **B 路线**：内置工具也直接做成插件，按功能拆成多个（不做成一个大插件）。
- **参考 deepseek-harness（v5 新增，见 §十一）**：采纳其「无特权核心 / 能力接缝 seam / bundle 发行 / 作用域注册 / 工具守卫 seam / 分层 patch」等架构原则，对 `plugin.json` 增 `seams` 字段、prompt 段加 `order`、工具守卫抽成插件、`.mpk` 对齐 bundle 术语、定义开源 discoverability 约定；但**不采纳其运行时 JS 动态加载机制**（违反 Apple 审核）。

## 二、统一插件标准 `.mpk`（强制规范，随项目开源）

### 2.1 物理格式
- 扩展名 `.mpk` = 标准 zip 归档（复用现有 `SkillManager.extractZip` 的 zlib inflate 解压逻辑）。
- 内部结构（固定）：
```
<plugin-id>/
├── plugin.json          # 必需：插件清单（唯一真相源，缺失则整个 .mpk 拒绝加载）
├── SKILL.md             # 仅 type:skill 必需（正文，沿用现有 SKILL.md frontmatter 格式）
├── models.json          # 仅 type:model 必需（能力声明 + auth/请求头，见 §四）
├── tools.json           # 仅 type:tool 必需（工具提供方声明，见 §三·B）
├── theme.json           # 仅 type:theme 必需（颜色/字体/token）
├── mode.json            # 仅 type:agent-mode 必需（运行模式）
├── mcp.json             # 仅 type:mcp 必需（MCP 服务器配置）
├── RULE.md / rules/     # 仅 type:rule 必需
├── PROFILE.md           # 仅 type:subagent 必需
├── SOUL.md              # 仅 type:soul 必需
├── fragment.md          # 仅 type:fragment 必需
├── whitelist.json       # 仅 type:tool.whitelist 必需
├── resources/           # 资源包：scripts/ references/ assets/ bin/ 等
└── README.md            # 可选：面向用户说明
```
> 注意：旧位图 `icon.png` **废弃**，图标统一走 SF Symbols（见 §2.4）。

### 2.2 `plugin.json` 字段（**强制**，最终以开源规范为准）

> **核心约定**：`type` 字段就是「这个插件用于调整哪个功能」的唯一声明。`plugin.json` 只承载**元数据**；具体能力声明写在对应子文件（`SKILL.md`/`models.json`/`tools.json`/`theme.json`/`mode.json`/`mcp.json`/`RULE.md`/`PROFILE.md`/`SOUL.md`/`fragment.md`/`whitelist.json`）里，按 `type` 决定。

```json
{
  "id": "com.miniclaw.skill.code-reviewer",
  "name": "code-reviewer",
  "version": "1.0.0",
  "type": "skill | model | rule | subagent | theme | agent-mode | shell-tool | mcp | soul | fragment | tool.whitelist | tool",
  "category": "skill",                // 用于分类展示 + 默认图标（见 §2.4）；通常与 type 一致，可细分
  "minCoreVersion": "1.0.0",          // 依赖的底座最低版本（PluginManager 校验）
  "enabledByDefault": true,
  "dependsOn": ["com.miniclaw.core.ish"],   // 依赖（如 iSH 运行环境）；不满足则拒绝启用
  "conflictsWith": [],                       // 冲突插件 id；命中则禁止同时启用
  "author": "MiniClaw / 第三方",
  "license": "MIT",
  "icon": "wrench.and.screwdriver",   // SF Symbol 名；声明则优先使用，缺省按 category 取默认图标（见 §2.4）
}
```

**强制约束（v4 已决 #1）**
- `plugin.json` **必须存在且 schema 合法**，否则 `.mpk` 整体拒绝加载——**不做旧兼容兜底**，不存在"无 plugin.json 也能跑"的窗口。
- 现有内置技能在阶段 1 一次性补齐 `plugin.json` 升级为 `.mpk`；不再保留"只扫 `SKILL.md`"的旧路径。
- `id` 全局唯一；重复 id 拒绝安装（覆盖需先卸载）。

### 2.3 统一开发格式（一套目录、一份清单、按 type 填内容）

| `type` | 必需内容文件 | 说明 |
|---|---|---|
| `skill` | `SKILL.md` | 技能正文（沿用现有格式） |
| `model` | `models.json` | 模型能力声明 + auth/请求头（见 §四） |
| `rule` | `RULE.md` 或 `rules/` | 规则文本 |
| `subagent` | `PROFILE.md` | 子代理角色设定 |
| `soul` | `SOUL.md` | 人格 |
| `theme` | `theme.json` | 颜色/字体/token（v1 可选，见 §四·3 主题项） |
| `agent-mode` | `mode.json` | 运行模式（minimal/standard/power） |
| `shell-tool` | `resources/bin` 或 `resources/scripts` | iSH 工具/脚本（depends on core.ish） |
| `mcp` | `mcp.json` | MCP 服务器配置 |
| `fragment` | `fragment.md` | 提示词片段 |
| `tool.whitelist` | `whitelist.json` | 工具白名单（开关：启用哪些已注册工具） |
| `tool` | `tools.json` | 工具提供方：声明 AI 可调用的新工具（impl = script / mcp / native） |

> 开发者只做两件事：① 声明 `type`+`category`；② 按 `type` 填内容文件。加载/消费细节对开发者透明。

### 2.4 插件图标规范（统一 SF Symbols）
| 规则 | 说明 |
|---|---|

### 2.5 打包与安装（开源标准流程）
1. 开发者本地按固定目录组织插件 → `zip -r my-plugin.mpk my-plugin/`。
2. 安装入口：App 内「设置 → 插件 → 导入 .mpk」、或文件关联 `miniclaw://plugin/install?path=`、或文件 App 打开 `.mpk`。
3. 安装时 `PluginManager` 校验：zip 结构、**plugin.json schema（强制）**、id 唯一性、依赖满足、`minCoreVersion`、冲突仲裁、头/原生二进制安全扫描（见 §七）。
4. 解压到沙盒 `plugins/<plugin-id>/`，登记到 `pluginRegistry`（持久化启用状态）。
5. 启用后由对应扩展点消费（`SkillManager`/`ProviderStore`/`ThemeEngine`/`ToolRouter` 等改为先读插件注册表）。

### 三·B 工具插件化（讨论结论，v4 已决：B 路线 + 按功能拆多个）

**统一机制（新增 `tool` 插件类型）**
- 插件在 `tools.json` 声明工具：每个工具含 `name` / `description` / 输入 `schema` / `impl`（`script` | `mcp` | `native`）。
- 核心 `ToolRouter` 合并所有启用 `tool` 插件的声明 → 注册进可用工具表；`buildSystemPrompt` 的工具段从"硬编码全量"改为"拼装所有启用插件的工具声明"。
- 调用路由：
  - `impl: script` → 在 iSH(rootfs) 内执行插件 `resources/bin` 或 `resources/scripts` 下的脚本（复用 shell-tool 运行环境，`dependsOn: core.ish`）。
  - `impl: mcp` → 经现有 `MCPClient` / `RemoteMCPTool` 调起。
  - `impl: native` → 路由到核心内置工具实现（用于把**内置工具也登记为插件**）。

**与现有三项的关系（收敛）**
- `tool.whitelist`：决定"在已注册工具中，某 agent-mode 启用哪些"——是**开关**，不是来源。
- `shell-tool` / `mcp`：是 `tool` 插件的两种**实现方式**，不再各自独立成"功能来源"。

**内置工具 → 功能插件映射（B 路线，按功能拆多个，实读 `AgentRunService.swift` 注册表）**

| 内置 `tool` 插件 id | 功能 | 包含的内置工具 |
|---|---|---|
| `com.miniclaw.builtin.tool.files` | 文件读写 | FileReadTool / ListDirTool / FileWriteTool / FileEditTool |
| `com.miniclaw.builtin.tool.browser` | 浏览器 | BrowserTool / MiniClawBrowserUseTool |
| `com.miniclaw.builtin.tool.memory` | 记忆 | MemoryWriteTool / MemoryGetTool |
| `com.miniclaw.builtin.tool.shell` | 命令行 | ShellExecuteTool |
| `com.miniclaw.builtin.tool.media` | 图像/文档 | ReadImageTool / VisionAnalyzeTool / ReadDocumentTool |
| `com.miniclaw.builtin.tool.apple` | Apple 系统/设备 | AppleClipboard / Device / NLP / Notification / Open / Speak / Photos / Player / Reminders / Speech / Vision / Weather + HealthKit / HomeKit / Location / Maps / Media / NFC / Alarm / Bluetooth / Calendar |
| `com.miniclaw.builtin.tool.miniclaw` | MiniClaw 自身 | MiniClawOpenTool / MiniClawModelUseTool / MiniClawDebugTool / ConfigTool |

**v1 边界（与 #13 一致，见 §七）**
- 插件**新增**的工具：v1 仅支持 `script`（iSH）与 `mcp` 两种实现（无原生代码，安全/审核可控）。
- `native` 实现（插件自带原生 Swift 工具）= 属 `core.extension`，v1 **不做**；但「内置工具经 `native` 登记」例外——只把核心既有实现挂到插件清单，不引入第三方原生代码，随内置插件一并落地。

### 三·B-2 落地版（2026-08-31 实装，工具格式以本节为准）

实际实现与 v4 草案有 4 处收敛：

| 项 | v4 草案 | 落地版（实装） |
|---|---|---|
| 声明文件 | 单文件 `tools.json` | **一包多工具**：`tools/<name>.json`，主键 = 文件名（与 rule/subagent 多文件包同构） |
| 实现字段 | `impl: script \| mcp \| native` | `backend`：`"shell"`（默认，声明式命令模板）\| `"builtin"`（内置 Swift 工具登记）。MCP 不再由 tool 类型承载——走独立 `mcp` 类型插件（导入即合并） |
| 内置迁移范围 | 26 个内置工具拆 11 个包 | **只迁系统能力类 9 个 + 记忆 2 个**（不依赖 sessionID 的 Apple 系 / config / 模型切换 / 记忆）；会话耦合类（文件 / 浏览器 / shell / 会话 / 技能 / 子代理 / 调试）**不迁**，保持核心无条件注册 |
| 启停语义 | 插件开关 | 插件开关；**记忆工具包例外**——以「设置-记忆-启用记忆」为单一真相源（见 §十二） |

**实现要点（实读结论）**
- 模型调用参数以 **JSON 经 stdin** 传给命令模板：引擎用 `cat <<'MINICLAW_IN_<随机>' | <command>` 包裹，单引号定界符零展开零转义；**管道必须与 `cat` 同一行**（`|` 开头的独立行是 sh 语法错误——真机实测翻车点）。
- 执行复用 `shell_execute` 同一运行时：`/bin/sh -c`、会话目录隔离（`/var/MiniClaw/sessions/<uuid>`）、环境变量注入、隐私模式掩码、超阈值转 offloads。
- 确认策略不自建：`resumePolicy = .requiresUserConfirmation` + 引擎级全局阀门「设置-通用-每次工具调用前确认」。
- 重名拒绝注册：与内置 / 先注册插件 / MCP 同名时跳过并日志（模型按名精确调用，重名即歧义）。
- 首启兜底：内置包未同步完成时按内置能力**全量注册**，内置工具绝不因同步时序消失；记忆工具仍受记忆总开关约束。
- 缓存代价：工具集变化（启停任一 tool 插件）会让服务端前缀缓存从 tools 段断一次，属设计内。

## 四、模型插件协议（你详细描述的机制，落地为标准）

### 4.1 三方职责（关键：插件只声明，不拉取）
| 职责 | 归属 | 说明 |
|---|---|---|
| 拉取模型列表 | **App 核心**（模型列表引擎） | 始终向 API `/models`(或兼容端点) 拉取 |
| 模型 ID 匹配 | **App 核心** | 拉取到的模型 ID → 在插件声明的 `models.json` 中查能力；未命中走启发式兜底 |
| 能力声明 | **模型插件**（`models.json`） | 声明某模型 ID 的能力，不列全量 |
| 请求构造/认证/流式解析 | **适配器（底座）** | 按插件声明的「请求头标准格式 + 认证方式」构造请求 |
| 内置兜底目录 | 内置模型插件 | OpenAI 兼容 / Anthropic 兼容 / DeepSeek 三族各自一份 `models.json` 能力声明 |

### 4.2 `models.json` 结构（草案）
```json
{
  "compat": "openai_compatible",
  "auth": {
    "methods": ["apiKey", "oauth"],
    "headerFormat": {
      "authorization": "Bearer ${API_KEY}"
      // extra: 可选；默认不声明（附加头走现有 customHeaders 手动配置，见 §四·3）。
      //   若开放插件 extra 头则在此声明任意附加头，并启用 §四·3 护栏。
    }
  },
  "baseURLHint": "https://api.openai.com",
  "models": {
    "gpt-4o": { "contextWindow": 128000, "maxOutput": 16384, "deepThinking": false },
    "o3":     { "contextWindow": 200000, "deepThinking": true, "thinkingLevels": ["low","medium","high","xhigh"] }
  },
  "capabilities": {
    "supportsResponseFormat": true,
    "supportsParallelToolCalls": true,
    "supportsPromptCaching": true
  }
}
```
- **复用现有字段**：`LLMProvider.customHeaders` / `credentialType`(apiKey|oauth) / `appendV1Suffix` / `customUserAgent` 直接承接「用户声明的请求头标准格式与认证方式」，无需另造。
- **复用现有能力结构**：声明映射到 `BuiltinModelInfo` + `ProviderCapabilities`（已存在），`modelCapabilities(for:)` 查询逻辑不变。

### 4.3 模型插件 `extra` 请求头：可选能力 + 安全护栏

> **开关决策（v4 已决 #2 的细化）**：默认**模型插件不允许声明 `extra` 请求头**——附加头一律由用户在现有 Provider 设置里手动填 `customHeaders`（即今天的流程）。此时**本节所有护栏都不需要**，因为不存在"不可信第三方插件注入任意头"的攻击面。
> 若后续要开放"插件自带 extra 头"（例如方便中转网关一键配好头），再启用下方护栏方案。本段保留护栏作为「启用时的规范」。

**目标（仅当开放 extra 头时）**：相对开放（允许声明任意业务头，兼容中转网关），但保证不破坏请求完整性、不引发安全问题。

**(1) 三层头来源**
- **底座固定头**：协议/传输层必须的（`Content-Type`、`Content-Length`、`Transfer-Encoding`、`Connection`、`Host`），由 URLSession/适配器管理。
- **auth 段生成头**：`Authorization`、`API-Key` 等，由 `auth.methods` 生成。
- **extra 头**：插件 `auth.headerFormat.extra` 声明的任意键值（业务/网关透传）。

**(2) extra 头护栏（保证不引起问题）**
- **保留键黑名单**：extra 中若出现 `Host` / `Content-Length` / `Transfer-Encoding` / `Connection` / `Content-Type` / `Authorization`（当 auth 段存在时）→ **静默忽略并记日志**。这些核心/认证头由底座或 auth 管理，防止插件意外破坏请求。
- **CRLF 注入防护**：键或值含 `\r` / `\n` → **拒绝该插件加载**（校验失败），防 header injection / 请求走私。
- **长度上限**：单键 ≤ 256 字节，单值 ≤ 8192 字节，总 extra ≤ 32KB；超限拒绝。
- **键字符白名单**：键仅允许 `[A-Za-z0-9-]`（标准 HTTP header 名字符集），非法键拒绝。

**(3) `Authorization` 取舍（关键，需你知晓）**
- 若插件声明了 `auth` 段（apiKey/oauth）→ `Authorization` 由 auth 机制生成，**extra 里再写 `Authorization` 会被忽略**（避免两个来源打架）。
- 若插件未声明 `auth`（纯匿名/自定义透传网关）→ extra 允许写 `Authorization`（由用户自己负责）。
- 取舍理由：避免"插件既用 auth 段又用 extra 覆盖 Authorization 导致认证错乱"。

**(4) `User-Agent` 取舍**
- 允许 extra 覆盖 `User-Agent`（现有 `customUserAgent` 机制延续），但 UI 提示"修改 UA 可能影响某些 API 的兼容性/风控"。

**(5) 信任分级**
- **内置模型插件**（随底座发布、经审核、系统签名）→ extra 头完全信任，跳过黑名单告警（仍过 CRLF/长度校验）。
- **第三方插件** → 执行上述全部护栏；且 extra 头在「设置→模型插件→请求头」里可见、可编辑、有风险提示文案"自定义请求头可能影响请求安全与隐私"，提供删除入口。

**(6) 取舍点汇总**
- **是否开放插件 extra 头（当前默认：不开放）**：开放则启用上方全部护栏；不开放则走现有 `customHeaders`，护栏不需要。你的当前倾向 = 不开放，故本节护栏暂不启用。
- （若开放时的细节）取舍 A：`Authorization` 与 `auth` 段互斥；取舍 B：保留键黑名单不可覆盖（安全底线）；取舍 C：`User-Agent` 开放覆盖带提示。

### 4.4 用户自建模型插件的开发边界（写进开源规范）
- ✅ 可声明：compat 族、auth 方法与请求头格式、baseURL 提示、已知模型能力、厂商级 capabilities。
- ❌ 不可/不需：拉取模型列表（App 负责）、硬编码全量模型、实现传输层（底座适配器负责）。
- 效果：做好一个 OpenAI 兼容中转网关插件，写好 `auth.headerFormat` 与 `capabilities`，App 拉到该网关模型列表后按 ID 匹配能力并正常请求。

### 4.5 内置模型插件 `com.miniclaw.builtin.models` + 7 厂商隔离（v4 已决）
- 唯一系统模型插件，随底座发布，默认启用且**不可卸载**（可禁用单族）。
- 内含 3 份 `models.json`（openai_compatible / anthropic_compatible / deepseek），即现有三个保留适配器的能力声明合集。
- **活动体系保留 3 族**：`openai_compatible` ← 原 openai+custom+自建 OpenAI 系；`anthropic_compatible` ← 原 anthropic；`deepseek` ← 原 deepSeek。
- **被移出活动体系的 7 个厂商（留代码、隔离、不引用）**：`google`/`openRouter`/`grok`/`qwen`/`xiaomi`/`zhipu` 及单独的 `custom`。源码保留在 `Services/Providers/Deprecated/`，参与编译但**不被 `ProviderType`/`LLMProviderFactory` 引用**；老用户配置提示「该厂商已移出活动体系（源码保留），请用对应兼容插件或自定义模型插件」。

## 七、安全与审核边界（v4 已决 #4/#5）

**1. 第三方原生扩展（core.extension）：v1 明确不做**，且规范明确禁止插件携带 Apple 不允许的代码：

- 审核友好：所有第三方插件源码可见（开源规范）；`.mpk` 安装时由 `PluginManager` 做静态扫描——**含原生二进制即拒绝基础审核风险检查**（仅允许 resources/ 下的脚本/文档/配置）。

**2. 模型插件请求头安全**：见 §四·3（保留键黑名单 + CRLF 防护 + 长度/字符校验 + 信任分级）。

**3. 依赖与冲突仲裁**：`dependsOn` 不满足 / `conflictsWith` 命中 → 禁止启用并提示用户。

- **目标**：minimal/standard/power 模式插件；`buildSystemPrompt` 按 mode 选段（minimal 不挂额外工具/不注入记忆 rules）。
- **真机验证**：极简模式对话中工具与记忆/规则注入符合预期。

### 阶段 11｜命令行/iSH shell-tool
- **目标**：预置脚本/二进制做成 `shell-tool` 插件（dependsOn core.ish）。
- **真机验证**：iSH 工具在插件启用时可调，禁用时不可调。

### 阶段 12｜MCP 收口 mcp
- **目标**：MCP 配置归入插件系统（`mcp.json`）。
- **真机验证**：MCP 服务器工具可用、可禁用。

> 共 13 个阶段（0–12），每个阶段独立 commit + 真机闸门。顺序逻辑：先建运行时（0）→ 低风险内容搬家（1–4）→ 核心工具（5）→ 模型与配置（6–8）→ 新增扩展点（9–12）。

## 十一、参考 deepseek-harness 的启发与调整（v5 新增）

> 来源：[deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)（DeepSeek 官方 agent harness，口号 **"Everything is a Plugin"**，基于 Cordis 插件框架）。本节只借鉴其**架构方法**，不照搬其运行时机制（见 §11.5）。

### 11.1 dsh 的关键设计（实读结论）
- **无特权核心**：模型适配器、工具注册表、会话日志、agent loop 本身都是插件，都可被配置替换；扩展 = 在别的插件旁挂一个新插件，注册是"插件卸载时自动撤销的 effect"。
- **能力接缝 seam + 事件瀑布**：扩展点叫 seam（如 `ctx.web`、`bash executor seam`、`ctx.tools`、`ctx.systemPrompt`、`ctx.llm`）；插件 `description` 写明挂哪个 seam，依赖列表即声明需要哪些 seam。工具执行是 `tools/pre-execute → execute → post-execute` 瀑布；`user-approval` / `sandbox-policy` / `tool-call-timeout-policy` 都是**独立插件**挂在 guard seam 上。
- **prompt 段注册契约**：`PromptSection` 有唯一 `name`（重名抛错）+ 升序 `order`（约定 `-100`=harness 身份、`0`=默认），系统按序拼接；`AssembleContext` 支持 `scope`（按 agent 作用域注册，子代理拿到专属段与工具）。
- **bundle = 发行格式**：bundle = Cordis config rows + 挂载代码，可被上层 patch；运行实例由 profile 组合多个 bundle，按层叠加（bundle 顺序 → profile patch → home patch → CLI patch），上层可改下层任意 config row。
- **discoverability**：GitHub `dsh-plugin` topic。
- **诚实标注不稳定**：自标 developer preview，会有 breaking changes。

### 11.2 对我们的调整（落地点 + 优先级）

| # | 调整 | 对应 dsh 概念 | 落地点 | 优先级 |
|---|---|---|---|---|
| A | `plugin.json` 显式加 `seams:[...]`，底座维护"已知 seam 注册表"，未知 seam 拒绝加载 | seam 是一等公民 | §二 字段、PluginManager 校验 | v1 必做 |
| B | prompt 段贡献型插件（fragment/rule/soul/skill）声明 `sectionName`(唯一)+`order`(整数)，重名即报错 | PromptSection name/order | §二 段文件、`buildSystemPrompt` 拼接 | v1 必做 |
| C | 新增 `tools.guard` seam；把核心硬编码的「审批/沙箱/超时」抽成 3 个内置 guard 插件，执行流水线 pre-execute 依次调用，可单独关 | tools/* guard 插件 | §三·B、阶段 5 | v1 必做 |
| D | 分层组合：内置插件=基础层(固定顺序)，用户安装=覆盖层；支持对内置插件特定配置做 patch 覆盖（无需 fork .mpk） | profile/bundle 分层 + patch | PluginManager layer | v1 仅做"启用/禁用+内置不可删"，patch 覆盖 v1+ |
| E | `.mpk` 规范里也称 "bundle"，统一术语；定义开源 discoverability：`miniclaw-plugin` topic + 仓库命名 `miniclaw-plugin-<id>` | bundle 术语 + topic | §九 规范仓库 | v1 必做(术语) / 文档 |
| F | subagent 插件天然成为"作用域"；插件可声明 `scope:"subagent.research"` 使贡献仅在该作用域生效 | AssembleContext.scope | §三 subagent、阶段 3 | v1 必做(至少 subagent 自带 scope) |
| G | **边界声明**：只学方法不照搬机制——不引入运行时 JS/原生动态加载（违反 Apple 审核）；`.mpk` 维持声明式 | — | 全篇 | 原则 |

### 11.3 对阶段计划的修订（对应 §八）
- **阶段 5（tool）扩充**：除 11 个内置 `tool` 插件外，新增"抽 `tools.guard` seam + 3 个 guard 插件（approval/sandbox/timeout）"——对应 C。真机验证加一项：关掉 approval guard 插件后工具不再弹审批。
- **阶段 2 / 4 / 8（rule / soul / fragment）**：段文件加 `order`——对应 B。
- **阶段 3（subagent）**：subagent 插件自带 scope——对应 F。
- **阶段 0（底座）**：PluginManager 加"已知 seam 注册表 + 未知 seam 拒绝"——对应 A；`.mpk` 术语标注 bundle——对应 E。
- **阶段 6（model）**：`models.json` 声明 `seams:["llm.adapter"]`，统一——对应 A。

### 11.4 明确不采纳的部分（重要）
dsh 用 Cordis 在**运行时动态加载 npm 包**（含 JS 代码、热更新）。**iOS/macOS 受 Apple 审核约束，禁止运行时加载不可信原生/JS 代码（无 JIT、禁动态执行）**，且用户已决"原生扩展禁止"。因此：
- ✅ 采纳其**架构原则**（seam / 无特权核心 / bundle / 作用域 / guard seam / 分层 patch）。
- ❌ 不采纳其**运行时代码加载机制**；我们 `.mpk` 维持声明式（配置/资源/SKILL.md/iSH 脚本/MCP），第三方工具实现仅 `script`(iSH)/`mcp`，`native` 仅用于内置登记。
- 这恰好与用户已决的"原生扩展禁止""工具仅 script/mcp"一致，是同一约束的两个侧面。

### 11.5 一句话总结
dsh 验证了"一切皆插件"在工程上可行，并给出成熟范式：**扩展点 = seam、注册 = 契约（唯一名+序）、守卫 = 可插拔插件、发行 = bundle、组合 = 分层 patch**。我们拿走这套范式的方法论，装进 MiniClaw 的声明式 `.mpk` + SF 图标 + Apple 合规框架——既对齐行业实践，又守住 iOS 红线。

## 十三、插件类型生效语义总表（2026-08-31 实装版）

| 类型 | 生效语义 | 导入默认 | 开关位置 | 备注 |
|---|---|---|---|---|
| skill | 叠加共存；启用后进指令入口（`/` 菜单） | 关 | 插件列表/详情页 | 正文由 `skill_load` 渐进加载 |
| subagent | 叠加共存；启用 = 角色进入派发集 | 关 | 插件列表/详情页 | 一包多角色，主键 = 文件名 |
| rule | 叠加共存；按当前语言取用 | 关 | 插件列表/详情页 | 语言子目录随包分发 |
| soul | **排他单选**：启用即停用其他 soul，内置灵魂进草稿 `SOUL.builtin.md` | 关 | 插件列表/详情页 | soul 是用户数据，同名不覆盖 |
| mcp | **导入即合并**（业界 `mcpServers` 格式），无启停开关 | — | 无（列表不显示开关） | 删除插件连带删除其导入的 server |
| model | 模板显式添加（包内 `providers.json`），密钥用户自填 | — | 无（列表不显示开关） | 删除插件连带删除其导入的供应商 |
| theme | **无插件页开关**：启用唯一入口 = 外观页选用 | — | 外观页 | 列表行/详情页均不显示开关 |
| tool | 叠加共存；启用 = 工具进入可用清单 | 关 | 插件列表/详情页 | shell / builtin 双后端，见 §三·B-2 |
| tool（记忆包） | **特例**：启用态 = 设置-记忆-启用记忆（单一真相源） | 开 | 插件页 = 记忆页 | 防两套开关冲突 |

**跨类型共同铁律**
- 所有类型都出现在插件列表（用户据此确认内置是否真的装上）。
- 清单必带 `description`（≤30 字一句话；内置必填、第三方选填，缺省显示"无描述"）。
- 用户导入的插件**默认关闭**；内置沿用 `enabledByDefault`；用户手动开关过的持久化状态始终优先。
- 停用的插件不进任何入口（指令 / 角色表 / 规则注入 / 人格 / 工具清单）。
