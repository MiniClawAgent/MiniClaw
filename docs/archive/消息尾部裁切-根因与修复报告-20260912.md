## 二、根因链（症状 1：尾部被裁）

四层原因叠加，缺一不可。每一层都有真机日志实证。

### 第 1 层：测量宽度不一致 —— `sizeThatFits` 在「理想尺寸 pass」按屏幕宽测量

SwiftUI 会在三种 pass 里以不同宽度询问 `sizeThatFits`，其中**理想尺寸 pass 的宽度是未指定的**（`proposal.width == nil`），而旧代码退回**屏幕宽 402**，与真实内容宽 370 不符：

```
[STF] call=1 rawProposal=nil w=402.0 container=0.0 view=0.0 storage=784 binding=1584
```

按 402 排版 → 行数偏少 → 高度偏矮。而 `.fixedSize(vertical: true)` 会把这次答案当**理想高度**长期沿用。

**修法**：由宿主（cell）**显式传入真实内容宽**，并重排宽度解析优先级。

### 第 2 层：`maxContentWidth` 恒为 0 —— 内容宽从未送达

```swift
// ChatView.swift:1190
maxContentWidth: 0,          // ← 语义 = 不设上限
```

于是 `BridgedAssistantBlock` 里 `maxWidth>0 ? max(0, maxWidth-2*blockHPadding) : nil` **一路落 nil** ⇒ 既让 `.frame(maxWidth:)` 成为 no-op，也让传给 `MarkdownView` 的 `contentWidth` 为 nil。

**修法**：改由 `configureCell` 传真实 cell 宽度（`collectionView.bounds.width` → 内容宽 = 402 − 2×16 = 370）。

### 第 3 层：播种引擎与渲染引擎不同源（差 12.3pt ≈ 半行）

```
[SEED] idx=173 src=textkit h=1703.0 uiH=1699.0          ← 播种：裸 NSLayoutManager 自建栈 → 1699
FIRST-MEASURE CORRECTION cellH=1703.0 newH=1711.3        ← 屏上 MarkdownTextView → 1711.3
```

播种把矮值写进统一高度缓存 → 屏上 `sizeThatFits` 命中它 → cell 少 12.3pt → 尾行下半被裁。

**修法**：`measureAttributedStringHeight` 恢复其**文档已声明的原设计** —— 使用与渲染完全相同的类（离屏 `MarkdownTextView`）。

### 第 4 层（真凶）：后台高度预热用**异源栈覆盖同源真值**

`scheduleHeightPrewarm` 在后台 Task 里用**私有裸 `NSLayoutManager` + `NSTextContainer`** 测量，然后**无条件覆盖**写进统一缓存：

```
[STF] EXIT src=attach-unified-cache h=1712.0   ← 播种写的同源正确值
[STF] EXIT src=attach-unified-cache h=1699.0   ← 被预热覆盖成矮值
[STF] EXIT src=attach-unified-cache h=1711.3   ← 修正写回后恢复
```

时间线完美解释「装机后首次/约 30s 后出现、重进会话即自愈」（预热有 30s 去重）：

1. 进会话：播种写 1712（正确）
2. 预热触发（30s 去重）→ 覆盖成 1699
3. 之后创建的 cell 全部 1703 → 被裁
4. 修正把 1711.3 写回缓存 → 再进会话就稳定

**修法**：预热**只补不覆盖**（`storeHeightIfAbsent`）—— 它的职责是「补齐缺失」而非「覆盖既有」。

### 第 5 层（换会话后仍裁的特殊形态）：播种输入 ≠ 渲染输入

含附件（表格/代码块）的块，播种测的是 `block.cachedAttributedString`，而**渲染路径会重新渲染**（附件实例与 renderer 身份耦合，不能跨上下文共享）⇒ 两者**输入不同**，实测差 18pt（≈一行）：

```
[SEED] idx=51 src=textkit h=1365.0 uiH=1361.0 n=1289    ← 播种（缓存串）
[STF] branch=cache-hit w=370.0 h=1379.0 len=1290         ← 渲染路径（新渲染串）
```

矮值一旦进缓存 → 屏上命中它 → **SwiftUI 只在首次询问时记住 representable 高度**，之后即使算出 1379 也不会触发 hosting 重测（`invalidateLayout()` 只能重跑 PLAF，读到的还是缓存的 hosting 尺寸）⇒ 末行永久被裁。

**修法**：含附件块**不回写**统一缓存；权威值改由渲染路径按新渲染串写回。非附件块输入与渲染完全一致（`pending = pre`），照常回写。

## 三、根因（症状 6：文件指示器错位）—— 浮点精度吞掉排序

`MiniClawChatAdapter` 把消息正文按工具事件位置切段，**尾部片段（= 最终回复）**的排序基准写的是：

```swift
// 旧
splitFileBlocks(markdown: segment, messageID: message.id,
                baseOrder: Double(Int.max - 1), startOffset: textCursor)
```

| 量 | 值 |
|---|---|
| `Double(Int.max - 1)` | ≈ 9.22e18 |
| 该量级下 Double 的精度间隔（ULP） | **2048** |
| 内部子序 `baseOrder + 0.05 * k` | **被完全吞掉** |

⇒ 尾部里的**文本块与文件块拿到完全相同的 order** ⇒ `sorted`（Swift 不保证稳定）把文件块排到正文之前 ⇒ 「文件指示器总在最终回复上面」。

> 该文件第 110-112 行的注释**早已记录同款坑**：「若只按元组排序不写回，渲染层读默认值 `Int.max-1` 会全部相等 → 按 id 乱序」。同一个 `Int.max-1` 被重复使用。

**修法**：基准改为基于**实际最大事件 order**，保持在 Double 精确区间内：

```swift
// 新
let tailBase = (sortedEvents.map(\.order).max() ?? 0) + 0.5
```

仍严格大于所有事件与该事件前的正文段（后者为 `eventOrder - 0.5`），子序 `0.05*k` 不再丢失。

## 四、根因（症状 7：文件点不开）

统一预览入口（`ChatView`）只有两条通路：

```swift
if url.isFileURL { fileURL = url }                            // ① file:// 绝对 URL
else { fileURL = MessageListModel.resolveMiniClawURL(url) }   // ② miniclaw:// 语义链接
guard let fileURL, FileManager.default.fileExists(atPath: fileURL.path) else { return }  // ← 直接 return
```

而 AI 在正文里写的是**裸路径**（相对名或裸绝对路径），且 `MiniClawChatAdapter.canonicalFileURL` 目前是**空实现**（原样返回）⇒ 两条通路皆不匹配 ⇒ `guard` 直接 return ⇒ **点击完全没反应**。

另有一处隐患：`FileBlockView` 用 `URL(string: url)`，**含空格的路径返回 nil** → 点击直接失效。

**修法**：
1. 新增 `MessageListModel.resolveLooseFilePath(_:sessionID:)` —— 绝对路径直接判定；相对路径**依次复用既有统一解析器**（`miniclaw://{workspace,mounts,attachments,shared,offloads}/<path>`），首个真实存在者胜出。**不新增第二套机制**。
2. `FileBlockView` 点击前先按 `urlPathAllowed` 百分号编码，兼容含空格/中文的路径。

**核心不变式（本次沉淀）**：
1. **一个高度值，一个测量源** —— 播种 / 渲染 / 估算 / 预热必须读取同一个通道，估算不得写入权威缓存。
2. **测量与渲染同源** —— 同宽度、同引擎、同输入；三者任一不同都会差一整行。
3. **自愈公式的增量必须与被调量解耦** —— 否则正反馈跑飞。
4. **不得用「瞬时两量之差」充当常量** —— cell 与视图在复用态属不同内容代际。
5. **判断旧值能否用于新内容，要看「值属于哪个内容」**，而不是看「某个字段是否为空」（本工程里空值恰好是流式态的正常取值）。

## 九、附：本次排查走弯路的三个技术教训

1. **探针没有落盘 ≠ 函数没被调用。** `AppLogger` 的落盘是**实例级攒批**，内联 `AppLogger(category: "X").info(...)` 的临时实例只塞 1 条就释放 → **整行永久丢失**。必须用 `static`/stored logger 或 `AppLogger.shared.info(_, category:)`；需要函数返回值时应加**统一出口钩子**，而不是在部分 return 处加探针（一个有 6 个返回路径的函数会恰好藏住关键那一条）。这一条曾让我连错两轮。
2. **先把「这条路径是否真的经过该代码」证伪，再动手。** 用户气泡塌行那次，我直接改了宽度解析顺序，事后才发现该气泡**根本不经过 `MarkdownView`**（它是纯 SwiftUI `Text`）。判据：`[STF]` 全表中 `contentW=nil` 共 0 行。
3. **日志关联必须严格 1:1。** 用内容长度关联两侧日志时容差取 ±2 会把一个块配到相邻块，得出「矮 24pt」的**假阳性**；改成「容差 ≤1 且匹配唯一」后结论完全相反。
