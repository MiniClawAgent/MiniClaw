# MiniClaw 多轮对话缓存命中率偏低 · 根因报告

- 日期：2026-09-15
- 范围：主会话（Agent 对话）在 DeepSeek / OpenAI 兼容端点上的**提示词前缀缓存命中率**
- 方法：真机日志实测 + 两路只读代码审计 + 供应商官方语义核对
- 状态：**根因已定位并交叉验证；本次未修改任何代码**（`git status --porcelain` 为空）

---

## 0. 结论摘要

**主会话发出的请求不是「上一轮请求逐字节 + 新尾巴」的嵌套结构，因此服务端缓存只能命中开头那段 app 级恒定的 `[system + tools]`，整段对话历史每轮 100% 原价重算。**

- 命中数在真机上表现为**一个常数**（≈ `sys + tools`），不随历史增长；
- 未命中增量与 prompt 增量**恒为 1:1**（新增的每个 token 都原价）；
- 同 App 的另一个引擎（复盘/记忆整理，请求结构天然嵌套）命中率可达 **99.2%** —— 证明「供应商/网络/模型」都不是瓶颈，问题在**我方的请求结构**。

**结构化元凶**：`OpenAIProviderAdapter.resolveVolatile()` 把易变段作为**临时尾部 user 消息**追加到消息数组末尾，每次请求重新生成、**且不进入历史** ⇒ 上一轮请求的结尾在下一轮请求里不存在 ⇒ 两轮请求不构成前缀关系。

**影响量化**：命中率 ≈ `(sys + tools) / (sys + tools + 历史 + 本轮新增)`。历史一长，命中率单调下降 —— 用户观察到的 94.1% → 44.9%、以及随会话变长而走低，都是这个形态。

**三个判决性特征**

2. **miss 增量 = prompt 增量**：1406 = 1406；732 = 732。**历史每新增 1 token，就多付 1 token 全价**。
3. **边界跟着 tools 大小走**：换一组端点后 `sys+tools` = 14494，命中随之变成 14336 / 15488。⇒ 命中边界是「静态前缀末尾」，**不是**某个固定 token 间隔，也不是供应商的容量上限。

**它命中整段历史。** 差别只在请求结构：`SessionReviewService.swift:121-130` 构造的是平铺的 `[system][…真实 user/assistant…]`，**没有尾部临时易变消息**，天然满足 `请求 N+1 = 请求 N + 尾巴`。

### 1.3 排除法：为什么不是 tools、也不是键序

- `tools` 段**命中了**（17024 ≈ sys+tools）。
- 但 `.sortedKeys` 下 `messages` 键在 `tools` **之前**。若服务端按 **HTTP body 字节序**做前缀匹配，排在 messages 之后的 tools **永远不可能命中**。
- ⇒ **服务端不是按 body 字节序匹配**，prompt 装订序与 JSON 键序无关。因此 `tools` 侧的全部变化嫌疑（顺序、键序、动态描述）**都不是本 bug 的成因**，本次命中率问题必须落在 **messages/system 段**。

## 2. 供应商官方语义（判据来源）

DeepSeek 官方《上下文硬盘缓存》<https://api-docs.deepseek.com/zh-cn/guides/kv_cache>：

- 缓存命中的前提是**完整匹配一个「缓存前缀单元」**（不是"最长公共前缀自动复用"）。
- 缓存前缀单元的落盘时机有三类：
  1. **用户输入结束位置**；
  2. **模型输出结束位置**；
  3. 长输入/长输出中**按固定 token 间隔**截取。
- 官方例二明确指出：`A+B` 之后来 `A+C` **不命中**；系统会把公共前缀 `A` 落盘为单元，**第三次**请求 `A+D` 才命中 `A`。

⇒ 要拿到高命中率，请求序列必须让「上一轮请求」成为一个**会被完整重现**的前缀单元。这正是本 App 主会话不满足的条件。

## 3. 根因（P0）：请求不是前缀嵌套

### 3.1 机制

`MiniClaw/Services/Providers/OpenAIProviderAdapter.swift:363-380`

```swift
private func resolveVolatile(_ messages: [ChatCompletionMessage]) -> [ChatCompletionMessage] {
    var result = messages
    var volatileParts: [String] = []
    for i in result.indices {                     // 从 system 上剥下易变段
        if (result[i].role == "system" || result[i].role == "developer"),
           let vol = result[i].volatileSuffix, !vol.isEmpty {
            volatileParts.append(vol); result[i].volatileSuffix = nil
        }
    }
    guard !volatileParts.isEmpty else { return result }
    let annotated = String(format: String(localized: "env_snapshot_note"), volatileParts.joined(separator: "\n\n"))
    result.append(ChatCompletionMessage(role: "user", content: annotated))   // ← 追加为末尾临时消息
    return result
}
```

实际发出的消息序列：

```
请求 #1: [S][tools][u1][易变段₁]                  ← "用户输入结束"单元落在易变段₁ 末尾
请求 #2: [S][tools][u1][a1][t1][易变段₂]          ← 易变段₁ 已不存在（它从不写入历史）
```

- 易变段每次请求**重新生成**（时间/工具清单/环境变量/挂载/记忆/子代理清单/已加载技能正文），内容逐轮不同；
- 它是**瞬态字段**（`volatileSuffix` 刻意不进 `CodingKeys`，`ChatModels.swift:364-369`），**不落盘、不回放**；
- ⇒ 请求 #1 的结尾是一个**只出现过一次**的字符串，其"用户输入结束"缓存单元**永远无法被完整匹配**；
- ⇒ #1 的全部内容（含 `u1`）从 #2 起作废；**工具循环的每一轮迭代都重复这一损失**；跨用户轮同样如此。

### 3.2 与实测的吻合

- 为什么命中是**常数**：`[S][tools]` 是 app 级恒定前缀（所有会话、所有请求都相同），被服务端"公共前缀检测"落盘为单元 ⇒ 每次请求都命中它；而 messages 区域没有任何可重复的单元 ⇒ 命中**到此为止**。
- 为什么 miss 与 prompt **1:1**：messages 区域 100% 无法命中。
- 为什么对照引擎**能涨到 99%**：它的请求逐次是前一次的延长，官方例一的形态。

### 3.3 为什么 08-31 那次"修复成功"是误判（重要）

`.workbuddy/memory/2026-08-31.md` 记载：`.sortedKeys` 修掉键序抖动后，"命中天花板 4864tok → 单次 12416-14336tok（**sys+tools 全命中**≈4333+8176，与估算精确吻合）"，据此判定收官。

**那个"天花板 = sys+tools"正是本 bug 的症状，被当成了成功指标。** 键序修复是**必要**的（否则连 tools 段都保不住，会退化成几乎 0 命中），但它只把命中从"几乎没有"抬到"静态前块"，**历史部分从头到尾一次都没命中过**。这解释了此后命中率仍随会话变长而恶化（09-15 观察到 94.1% → 44.9%）。

- **`tools=…/约 631tok` 不是 MCP 发现竞态**：那是复盘分身引擎（`SessionReviewService.swift:55-64`）只注册 `memory_write` / `memory_get` 两个工具，量级 600~800 tok 与 631 吻合；MCP 缺工具只可能少若干工具，本地 16 个常驻工具仍有数千 token。触发点在「离开会话 / 进后台」之后。

## 5. 修复方案

### P0（拿走绝大部分损失）：让请求恢复前缀嵌套

| 方案 | 做法 | 代价 | 建议 |
|---|---|---|---|
| **A（推荐，正式）** | 易变段**仅在内容变化时**作为一条消息追加，并**持久化进该会话的 API 历史**（不显示在 UI、不污染用户可见内容）。 | 需动会话持久层：给 `ChatMessage` 增加 API-only 的快照字段，并在 `buildHistory` 中回放；每轮可能多几百~1k token 历史（**这部分本身可命中，成本极低**）。 | ✅ 目标态：前缀永远 append-only，命中率稳定 95%+，且不受整点/记忆写入/子代理派发影响 |
| **B（先验证用）** | 不再剥离，把易变段**拼回 system 末尾**（`resolveVolatile` 改成不 append）。 | 易变段一变（整点、派发子代理、记忆写入）整段前缀重置一次；但**远好于现状（每轮重置）**。 | ✅ 一行级改动，适合先拿真机数据钉死 P0 |
| **C（Gemini 专项）** | 把 Gemini 路径也改成 Anthropic 那样的独立 block / 尾部消息（对齐 `AnthropicProviderAdapter.swift:140-149,187-213` 的既有正确做法）。 | 小。 | ✅ 与 P0 同批 |

### P1（按收益排序）

1. `buildHistory` 回放工具往返与 `reasoning_content`（`AgentRunService.swift:172-182`，08-31 已列 Phase 2）——让上一轮工具内容也能进缓存，而非白扔；
2. `stablePromptCache` 加失效钩子（SOUL / 规则 / 插件开关变更时 invalidate）+ 淘汰换 LRU；
3. `/技能` 轮改为「stable 保持缓存版 + 技能正文走尾部注入」；
4. resume 后强制用当前 stable 覆写 `messages[0].content`；
5. `buildToolRouter` 补 `waitForBundledSync` 门禁（消除冷启动首轮工具集漂移）；
6. `dispatch_subagent` 的角色清单移出 schema（改为在易变段/tool 结果里下发），消除 tools 段唯一的动态内容；
7. `RemoteMCPTool`：同步发现失败也写入 `failures`；`warmupMCPDiscovery` 与主路径做 in-flight 去重；
8. `limitMessages` 的头部裁剪改为「只在压缩不可用时才启用」并加显式日志。

### 诊断设施（小改，但强烈建议先做）

- `AgentLoopEngine.swift:652-655` 的 `[Cache指纹]` 日志**补 `cacheSessionKey`**：`modelCallSeq` 是每引擎实例计数，复盘/子代理引擎首轮也显示 `#1`，与主会话首轮在日志里无法区分（这正是 631tok 被误读的原因）。
- `[Cache指纹]` 增加「本轮命中/未命中」与「命中边界 ≈ 哪一段」的对照输出，使"静态前块命中"这种病态形态一眼可见——**避免再次把"天花板 = sys+tools"当成功**。
- `reqdump`（`OpenAIProviderAdapter.swift:162-175`）保留策略从「最近 2 份」放宽到「最近 4~6 份」，便于跨多轮 diff。
